# Proposal 实验前科学门禁

## 定义

Proposal 是一份实验前科学论证合同。它承诺问题、主张、机制和检验方式是明确且可审计的，不承诺假设会被支持、指标会提升或论文会被录用。

每个候选必须压缩为：

```text
Q：精确研究问题
K：计划建立或否定的知识主张
M：适配研究类型的机制、设计依据、测量效度、形式关系或系统不变量
D：能够判定主张、区分最强替代解释或方案的决定性检验
C：正、负、混合或不可判定结果分别改变什么科学认识
```

同一 topic、数据集、理论来源、组件或评测框架可以复用。新颖性比较的是 `K` 以及支撑它的 `M/D` 是否与最近邻功能等价，而不是表面名词是否首次出现。

具体研究类型如何解释M/D见[问题到方案](problem-to-proposal.md#按研究类型解释m与d)。字段名称兼容现有运行时，不要求无关的因果中介或GPU实验。

## 四轴状态

Proposal、文献新颖性、实证进度和本地执行条件不得压成一个状态：

- `Proposal decision: pass|revise|reject`：实验前科学论证是否成立。
- `Novelty status: exploratory|provisional|audited`：有范围、有日期的新颖性证据强度。
- `Empirical status: not-run|pilot|tested`：实验实际进度；`not-run` 不降低 Proposal 决策。
- `Execution readiness: designed|deployable|blocked`：协议只有蓝图、当前环境可部署或受本地资源/授权阻塞。

`Paper sufficiency: insufficient|promising|proposal-ready` 只判断计划中的证据包能否形成完整论文论证，不预测录用，也不要求证据已经产生。

`Depth gate: pass|revise` 与 `Breadth gate: pass|revise` 独立记录在 `proposal/depth-breadth.md`。深度通过表示主张已超过描述性结果并形成可区分机制、测量效度论证或形式关系；广度通过表示中心问题拥有解释它所必需的子问题、边界和最小外部效度，同时有明确扩张上限。

## 非补偿性门禁

以下各项必须分别关闭，不能用加权总分相互补偿。候选评分只能用于排序。

1. **问题价值**：回答后会改变理论认识、评测方式、方法选择或系统设计，而非只增加一个分数。
2. **证据定位**：已有共识、冲突、未知和访问级别可追溯，关键近邻经过全文核验。
3. **范围内非等价性**：逐个最近邻写清 `inherited`、`new`、`scientific consequence` 和等价判断。
4. **问题树完整性**：一个中心问题和 2–5 个必要子问题共同支撑同一知识主张，不是多个独立 topic 拼接。
5. **机制深度**：主张由机制、形式关系、测量效度或系统不变量产生，而非事后故事；声明目标深度和适配的研究类型。
6. **竞争解释**：至少一个可信 rival 能解释相同表面现象。
7. **可区分与可反证**：主机制和 rival 预测不同的观测模式，并有会撤回主张的结果。
8. **必要广度**：确认性核心、必要边界、最小外部效度和可选扩展分层；每个纳入轴关联 claim、rival 或 threat。
9. **识别蓝图**：处理、对照、实验单位、结果、oracle、混杂控制和操纵检查原则上明确。
10. **纸面可行性**：数据、模型、代码、许可、算力上界和替代路径能够说明；GitHub artifact 只用于支撑这一项。
11. **结果知识价值**：正、负、混合和不可判定结果各有预先限定的解释，不能只有正结果有价值。
12. **论证完整性**：核心实验、强基线、机制检验、必要外部效度和 Artifact 路径共同支撑一条主论证。
13. **扩张纪律**：新增模型、数据、变量或方法必须改变一项主张、竞争解释、边界或外部效度判断，并有停止扩张规则。
14. **诚信与边界**：假设、限制、未覆盖来源、伦理和所需授权明确。

以下情况即使没有运行实验也属于 `proposal-fatal`：核心构念原则上不可操作化；没有可靠可观测结果或 oracle；所有机制给出同一预测；设计无法识别声称的因果关系；最近邻已覆盖同一知识主张与决定性证据；资源根本不可获得且没有替代方案；只有正结果可解释；核心假设循环包含结论。

以下属于 `empirical-dependency`，在 Proposal 阶段允许保持 `open` 或 `deferred`：实际效应量与显著性、操纵检查实际结果、模型成功率、跨模型稳健性、人工标注一致性、实际 GPU 时间、真实运行失败和 Artifact 复现结果。不得将它们提前标为已验证，也不得因尚未运行而拒绝 Proposal。

即使新颖性和最小实验可行，以下情况仍阻止 `Paper sufficiency: proposal-ready`：中心主张只依赖单一演示指标；必要子问题或过程—终点链缺失；主张范围超过计划中的总体/环境；完整论文只能依靠堆模型与数据集增加篇幅；或没有为确认性核心、必要边界与可选扩展设定清楚边界。

只影响最终论文充分性的扩展实验、完整 Artifact、表图重建和投稿模拟审稿归入 `paper-stage`。

## Threat register

`proposal/threats.jsonl` 每项至少包含：

```json
{
  "threat_id": "T1",
  "class": "proposal-fatal|empirical-dependency|paper-stage",
  "category": "novelty|mechanism|identification|measurement|feasibility|ethics|external-validity",
  "severity": "fatal|major|minor",
  "status": "open|mitigated|resolved|deferred",
  "threat": "威胁什么主张",
  "mitigation": "已完成的处理或后续判定门"
}
```

只有 `class=proposal-fatal` 且 `status` 不是 `resolved` 的条目阻止 `Proposal decision: pass`。如果一个威胁既可能使方案在原则上不可识别，又需要 Pilot 才知道是否发生，应拆成两项：先审查纸面识别条件是否存在，再把实际操纵结果登记为 `empirical-dependency`。

## 结果—贡献矩阵

Proposal 在运行前枚举主要结果模式，并为每项限定允许得出的结论：

| 结果模式 | 可支持的知识 | 不允许的外推 |
|---|---|---|
| 主机制预测成立 | 在预定范围内支持机制 | 不自动证明跨模型普适 |
| rival 模式成立 | 否定或收缩主机制，支持替代解释 | 不把失败改写成原假设成功 |
| 混合结果 | 确定交互、异质性或边界条件 | 不只选择有利子组 |
| 精确零结果 | 给出效应上界或排除一类解释 | 低功效时不得宣称无效应 |
| 不可判定 | 暴露测量、功效或资源限制 | 不将其包装为正/负结论 |

## GitHub 资源的使用边界

可借鉴现有科研 Agent 的流程模式：文献图谱支撑 Idea、生成多个异质候选、相似 Idea 去重、逐个最近邻碰撞、反方 reviewer、多轮反思和代码模板可行性检查。不得照搬其自评分、候选数量或自动审稿分数作为科学门禁。

GitHub 仓库可用于核验：代码是否存在、许可证、依赖版本、最近维护、数据下载路径、复现入口、issue 中已知失败和预计工程成本。star、fork、README 自述和仓库存在本身不证明论文影响力、新颖性、正确性或实验结论。
