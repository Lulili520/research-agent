# 内容评估与递归改进

## 一、文献调研如何评

| 维度 | 实际核验 | 常见不能通过的情形 |
|---|---|---|
| question-coverage | 用用户问题反查各必要分支、直接近邻和背景证据；检查未覆盖分支是否会改变答案 | 只围绕最初想法搜支持材料；排除理论/效率背景却不说明影响 |
| source-fidelity | 抽取中心主张回到原文，核对版本、定位、数字、范围和作者/读者推断 | 把摘要当方法证据；把作者猜想写成事实；引用不能支持该段 |
| method-understanding | 重建输入输出、关键公式、运行例子、边界及决定性实验，核对必要附录 | 漏掉决定行为的归一化/条件；只有模块名和摘要 |
| evidence-comparability | 检查数据、split、协议、预算和指标；解释冲突可否归因于条件 | 跨不兼容设置直接排数字高低；忽略强基线 |
| synthesis-and-gaps | 检查综合结论是否由比较推得，空白是否重要、真实且被最近邻检索挑战 | 拼卡片；把未搜索到称为无人研究；任意组件组合叫突破 |
| explanation-quality | 不看作者自评，用正文回答机制问题；检查图、例子、符号、链接与组织 | 图不可读或无解释；深度都藏在附录；长但无法回答具体问题 |

覆盖不等于论文总数，深度不等于字数。根据中心主张风险分配核验力度，同时随机检查非中心材料，防止只修被点名段落。对不可访问材料明示证据等级，不允许用完整字段假装已读。

### 正文可理解性独立核验

先读取目标读者及允许前提，再暂时不借用原文，实际完成正文任务：还原方法、走通新例子、推演条件变化、判断证据边界。保留回答和支撑它的正文位置，记录哪些步骤必须借助未介绍的背景或评审既有知识。回查原文另做忠实性审查；两项不能互相替代。方法图存在、符号定义齐全和解释变长都只是线索，不是验收。

报告 metadata 中的 `reader_contract` 声明 audience、assumed_knowledge 与 required_checks；这些要求由当前用户意图决定，不将初学者要求套到所有专业交流。每个 reader_check 练习包含实际问题、回答、正文证据与 gaps。关键路径缺口必须成为实质 finding；没有真实人类读者时只称“模型辅助文本审计”，限制字段须明确模型先验可能掩盖缺口。

检查集同时含未被作者点名的论文/段落，避免只润色几个示范。比较新旧正文时固定相同读者与问题；可以报告哪些具体解释已补齐，不能据非盲、预算不等的修订宣称整个 Agent 已获泛化提升。真实人类理解率需另行获得合法受试与测试证据，不能由模型评分替代。

## 二、方案设计如何评

| 维度 | 核验问题 | 需要返回的动作 |
|---|---|---|
| scientific-value | 消除的是什么重要不确定性，影响谁，为什么值得投入？ | 重新界定问题或放弃低价值分支 |
| nearest-neighbor-difference | 与最强工作差异在哪一条机制/知识/适用条件，能否复核？ | 反向补检、直接比较或收缩主张 |
| mechanism-and-assumptions | 为什么会奏效，假设合理吗，推导/不变量是否成立？ | 理论核验、构建反例或改机制 |
| implementation-specificity | 给定材料，第三方知道如何实现关键步骤吗？ | 操作化变量、接口、算法和最小例子 |
| discriminating-tests | 哪个检验能区分核心解释和最强替代解释？ | 重设处理、对照或验证逻辑 |
| feasibility-and-risks | 材料/算力/人力可否获得，哪里可能失败，有何替代？ | 小规模可行性设计、估算或否决 |

测量和严谨比较也可以产生新知识；不因缺少新模型/形式定理而否决。实验未运行只是 empirical status，不能冒充验证通过，也不自动成为 proposal-fatal。

### 方案的整体理解

先做一次不提供作者解释或术语提示的正文阅读，记录第一次能重建什么、在哪里回读、需要哪些正文未提供的知识。问题可以是“这项研究解决什么实际困难、相较已有做法改变哪里、怎样判断值得继续”，不要在题干先讲完答案。使用模型时无法清除其专业先验，只能保留回答依据与限制，不能冒称真实新手体验。

随后检查正文中同一例子的完整处理链，以及核心实验、必要对照和条件性扩展的区别。每个连接都要在报告中有解释；评审自行拼接的推导、编写的样例或从其他材料借来的步骤要标为补充，不得算作正文已经包含。另用新例子验证迁移，区分“已有解释的应用”与“替作者补写算法”。

检查任务依据研究问题与读者背景确定，可在报告的 `reader_contract` 中登记为 `overview-reconstruction`、`end-to-end-trace`、`priority-and-scope` 等名称。实际作答记入 `reader_check.exercises`，实质缺口关联相应的 finding。整体机制、收缩理由或工作性质不清时，返回机制、实现或价值维度的修订；公式题通过不抵消该缺口。读者能准确复述仍只是必要证据，还要检查频繁跨章拼接、概念先用后解、层次混杂与不必要的阅读负担。

解释性修订须复核整篇组织和处理链，确认已记录的阅读障碍得到解决。版本比较使用相同目标读者和整体问题，依据可定位的解释差异判断效果；新增定义、篇幅或格式本身不代表改进。科学约束若在改写中丢失，同样返回修订。

## 三、从评估到下一动作

一个有效问题记录应足以让另一名 Agent 执行和复核，例如：“第 3 节将预算收益解释为数据质量收益，但来源表 2 的训练步数不同；回读配置并建立同预算对照，否则收缩机制主张；关闭条件是新版本明确区分两个解释并给出可识别检验。”

问题分 fatal（中心主张/识别不可成立）、major（重要证据或机制尚缺）、minor（不改变判断的表达/局部改进）。同样的问题在不同主张下严重性可能不同。

负责人优先选择能改变中心判断、候选排序或可行性的动作，并考虑证据获取成本。无需给任意加权总分。每次动作记录预期改变什么判断；实际没改变也保存，避免重复无效检索。

来源/正文/设计任一实质变化，重新审受影响结论。未变化部分保留证据，但旧验收不可自动套用新正文。旧问题必须显式 resolved/retained/withdrawn；代码成功退出不能关闭科学问题。

## 四、历史库与候选演化

研究版本保存：正文与图、原始来源版本、知识节点及关系、评审输入包、缺口、改动原因、结果和下一动作。Idea 通过有版本的节点以及 derived-from/contradicts/addresses 等关系形成演化分支；被否决方向仍可被新证据重新打开。检查点可有多个父节点，表示合并而非覆盖。

Agent 版本保存：运行时、Skills、流程和测试的完整快照；每个 Worker 请求绑定系统版本。系统候选独立于研究候选，不因为某份报告看起来更好就改全局规则。

对失败先区分来源访问、召回遗漏、理解错误、综合跳步、设计不可判别、执行接口或评估误报。只有能说明因果链的通用问题才值得调整框架；具体会场、论文和资源写回课题，不污染通用规则。

## 五、框架改进的评估设计

1. 保存基线、失败输入、真实输出、来源依据和错误位置；提出局部改动假设与可能回归。
2. 在隔离目录生成候选，避免评估过程中修改基线。固定任务集、可用来源/工具、模型条件、预算和评估器。更换评估规则是另一个待评改动，不能同时更换标准又宣布胜出。
3. 用同任务配对运行基线与候选；随机隐藏 A/B 身份，评审只看问题、原始证据和输出。先独立判错，再做偏好比较，记录分歧与理由。
4. 同时包含已知失败、正确对照、不同研究类型和未用于修改的保留任务。已知失败修复不能证明泛化；不要向生成者泄露保留任务标签。
5. 报告有来源支持的缺陷检出/漏检、误报、机制重建、有效修正、重新打开率、来源成本/调用成本与研究设计判别力。统计的分母和不确定性必须明确，不只报平均“质量分”。
6. 有明确改善且无未解决严重回归，才提出接纳；无法区分就 inconclusive，有退步就保留基线并记录失败。接纳记录不自动部署，旧版本和评估输入继续可追溯。
7. 真实使用的新失败进入回归池；定期刷新保留任务，避免围绕固定题库过拟合。回退追加事件，说明触发证据，不删除失败历史。

运行时能检查这些记录是否一致，不能证明评审真的读懂论文或评估结果没有偏差。独立上下文也不是独立专家真值。高风险结论需要原文复核、真实执行证据，必要时人工领域专家核验。

## 六、停止与能力边界

报告达到当前问题要求、重大缺口已独立复核后可以交付，并继续接受新证据更新。达预算、不可访问、缺少工具或授权分别暂停，不能记为通过。单元与合成集成测试验证状态机制；真实科研能力需用实际模型、原文证据和盲评验证。
